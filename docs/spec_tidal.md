# 宣言的 UX 仕様検証システム 要件定義書 v0.1

**仮称：Declarative UX Verifier**

- 文書種別：要件定義書
- 対象：Web アプリケーション
- 初期対応：React / Solid / Svelte
- 開発言語：TypeScript
- 実行環境：Node.js / Playwright
- ステータス：実装着手用ドラフト

---

# 1. システム概要

## 1.1 目的

本システムは、Web アプリケーションのユーザー体験（UX）に関する期待動作を宣言的な仕様として記述し、実装がその仕様を満たしているかを検証するためのツールである。

従来の E2E テストが具体的な操作手順と期待結果を記述するのに対し、本システムでは、状態、イベント、状態遷移、禁止条件、到達可能性などを定義し、それらから検証経路を生成する。

システムは以下の3種類の検証を区別して実行する。

1. **モデル検査（Model Checking）**：仕様として定義された抽象状態モデルの性質を検査する。
2. **適合性検査（Conformance Checking）**：モデルが予測する状態と、実際のアプリケーションから観測した状態を比較する。
3. **具体値検証（Concrete Oracle Verification）**：抽象状態だけでは検出できない具体的なデータ損失や値の不一致を、独立したオラクルによって検証する。

これらの検証結果を区別し、検証範囲、証拠、未評価対象、反例を含む機械可読レポートを生成する。

## 1.2 コアバリュー

### CV-01：宣言的な UX 仕様

利用者が個別のテスト手順を大量に記述するのではなく、アプリケーションに期待する状態遷移と性質を宣言する。

### CV-02：フレームワーク非依存性

React、Solid、Svelte などの内部リアクティビティやコンポーネント機構に依存せず、ユーザーが観測・操作できる振る舞いを検証対象とする。

### CV-03：仕様と実装の独立性

抽象モデルと具体的なアプリケーション実装を分離する。

モデル検査が成功したことを、アプリケーションの正しさの証明として扱わない。

### CV-04：反例駆動の検証

性質の違反が検出された場合、可能な範囲で再実行可能な最小の操作列と観測結果を出力する。

### CV-05：不確実性の明示

検証できなかった場合、無条件に成功または失敗と判定せず、探索不足、観測不一致、アダプター障害、再現性不足などを区別する。

### CV-06：再現可能な検証

同一の仕様、設定、モデルに対して、モデル検査部分は決定的な結果を出す。

ブラウザーを用いた実行は、初期条件の隔離、証拠保存、再実行によって再現性を高める。

# 2. 対象範囲

## 2.1 初期対応範囲

- Web アプリケーションの UI 状態
- ユーザー操作に伴う状態遷移
- ブラウザー操作に伴う状態遷移
- 外部環境による非決定的な状態遷移
- 到達可能性・禁止遷移・脱出可能性の検証
- DOM / ARIA / testid に基づく状態観測
- Playwright を用いた操作実行
- 具体的な入力値・保存値の検証
- モデルと実装の状態不一致の検出
- 反例および再現情報の出力
- Golden Tests による検証器自身の検査

## 2.2 対象フレームワーク

初期受け入れテストでは以下を対象とする。

- React
- Solid
- Svelte

ただし、フレームワークごとの内部状態 API は初期版の必須機能としない。

標準 DOM とブラウザー API で操作・観測できる場合、共通 Playwright アダプターを使用する。

## 2.3 初期対象外

- React Hooks、Solid Signals、Svelte Runes 等の内部状態の直接検証
- フレームワーク固有のレンダリングアルゴリズムの検証
- 任意のアプリケーションからの完全自動モデル生成
- アクセシビリティ規格への網羅的適合性検査
- 視覚的回帰テスト
- 性能・負荷テスト
- セキュリティ脆弱性検査
- 分散システム全体の形式検証
- TLA+ / Quint への変換
- 無制限の状態空間探索

# 3. システムアーキテクチャ

## 3.1 基本構成

```text
              TypeScript DSL
                    |
                    v
              Compiler / Validator
                    |
                    v
                 spec.json
                    |
          +---------+---------+
          |                   |
          v                   v
     Model Checker       Trace Generator
          |                   |
          |                   v
          |               Test Runner
          |                   |
          |              binding.json
          |                   |
          |                   v
          |            Playwright Adapter
          |                   |
          |                   v
          |             Web Application
          |                   |
          |            +------+------+
          |            |             |
          |            v             v
          |       Observer      Concrete Oracle
          |            |             |
          |            +------+------+
          |                   |
          |             Conformance
          |                   |
          +---------+---------+
                    |
                    v
              Result Aggregator
                    |
                    v
                report.json
```

## 3.2 レイヤー分離

システムを以下のレイヤーに分離する。

| レイヤー | 責務 |
|---|---|
| DSL | 型付き仕様の記述 |
| IR | 仕様の中間表現 |
| Model Engine | 状態遷移・探索・性質検査 |
| Trace Generator | 操作列の生成 |
| Runner | 実行順序・再試行・隔離の制御 |
| Adapter | アプリケーション操作・観測 |
| Oracle | 独立した具体値検証 |
| Reporter | 判定の集約・証拠の出力 |

Model Engine はブラウザーやフレームワークに依存してはならない。

Adapter は Model Engine の内部実装に依存してはならない。

# 4. 仕様記述・IR 要件

## FR-01：TypeScript DSL

システムは TypeScript による型付き DSL を提供する。

利用者は以下を宣言できる。

- 状態変数とその値域
- 初期状態
- イベント
- ガード条件
- 状態遷移
- 検証プロパティ
- 探索設定

DSL はバージョン付き JSON IR に変換可能でなければならない。

## FR-02：JSON IR

JSON IR は TypeScript に依存しない独立した形式とする。

最低限、以下を持つ。

- `schemaVersion`
- `kind`
- `states`
- `initialState`
- `events`
- `transitions`
- `properties`
- `analysis`

IR は JSON Schema 等で構造検証可能とする。

未知の必須機能や未対応バージョンを黙って無視してはならない。

## FR-03：式の表現

ガード条件・プロパティ・状態更新は、解析可能な式木として保持する。

任意の TypeScript 関数を IR の中に直接埋め込まない。

式の評価について、次を定義する。

- 型
- 比較演算
- 論理演算
- 状態変数参照
- 未定義参照時のエラー
- 型不一致時のエラー

## FR-04：状態遷移

各状態遷移は、イベント、ガード、更新内容を保持する。

`when: false` はイベントがその状態で有効ではないことを意味する。

`set: {}` はイベントが有効であり、抽象状態を変更しないことを意味する。

両者を区別して扱う。

## FR-05：イベント分類

イベントは次の種別を持つ。

| 種別 | 内容 |
|---|---|
| `user` | ユーザーによる操作 |
| `browser` | リロード・戻るなどのブラウザー操作 |
| `env` | 保存成功・通信失敗などの環境イベント |

同一状態で同一の `user` / `browser` イベントに対するガードが重複し、異なる結果が生じる場合、原則として仕様エラーとする。

`env` イベントについては、明示的に非決定的な結果候補を保持できる。

## FR-06：抽象状態と具体値の分離

モデル内のデータは、必要に応じて次のような抽象値に縮約できる。

```text
empty
dirty
saved
```

具体的な文字列、識別子、保存内容などは、モデルとは別の具体値オラクルで検証可能とする。

抽象状態が同じであっても、具体値が異なる場合に違反を検出できなければならない。

# 5. モデル検査要件

## FR-07：状態空間探索

有限状態モデルを対象に、到達可能な状態と遷移を探索する。

最低限、以下を実装する。

- 到達可能状態の列挙
- 到達可能遷移の列挙
- デッドロックの検出
- 到達不能イベントの検出
- プロパティ検査
- 反例となるイベント列の出力

探索順序は決定的であること。

## FR-08：プロパティ

初期版は以下の性質をサポートする。

### neverTransition

指定した遷移が発生しないこと。

例：ユーザーが破棄操作を実行していないにもかかわらず、編集中の下書きが空にならないこと。

`unless` が指定された場合、例外となるイベントは当該遷移を発生させたイベントそのものとする。

### canReach

指定条件を満たす各到達可能状態から、目標条件を満たす状態に至る経路が少なくとも一つ存在すること。

### escapable

特定状態から、指定された操作種別によって脱出する経路が存在すること。

`by: "user"` はユーザーイベントのみを使用する。

`by: "any"` は全イベント種別を対象とする。

これらの到達可能性プロパティは、無限実行における必然的な進行や公平性まで証明するものではない。

## FR-09：空虚性検査

検証対象の前提状態が到達不能である場合、無条件に PASS としてはならない。

以下を確認する。

- 前提条件を満たす状態が到達可能か
- 対象イベントが実行可能か
- 対象プロパティが実際に評価されたか
- 検証に必要な状態・遷移が探索されたか

空虚性による判定不能は `INCONCLUSIVE` とし、原因を `VACUOUS` 等として記録する。

## FR-10：探索上限

次の制限を設定できる。

- 最大探索状態数
- 最大探索深度
- 最大遷移数

探索上限に達した場合、未探索領域に対する完全な検証が行われたものとして扱ってはならない。

探索不足により真偽が確定できない性質は `INCONCLUSIVE` とする。

既に発見された有効な反例は保持する。

# 6. アダプター要件

## FR-11：共通アダプター契約

アダプターは、少なくとも次の機能を提供する。

```typescript
interface UXAdapter {
  setup(): Promise<void>;
  reset(): Promise<void>;
  execute(event: BoundEvent): Promise<void>;
  observe(): Promise<Observation>;
  teardown(): Promise<void>;
}
```

これは概念上の最小契約とし、実装段階でエラー型や実行コンテキストを明確化する。

アダプターは内部の React / Solid / Svelte 状態を前提としない。

## FR-12：Playwright アダプター

初期実装では共通 Playwright アダプターを提供する。

以下をサポートする。

- ページ遷移
- クリック
- テキスト入力
- リロード
- DOM 属性・テキスト・入力値の観測
- ARIA / Role / testid による要素指定
- 条件に基づく待機
- ブラウザーコンテキストの初期化
- テストごとの状態隔離

固定時間 sleep を主要な同期方法として使用しない。

## FR-13：Binding 定義

`binding.json` により、抽象イベントと具体的な操作の対応を定義する。

含まれる情報は以下とする。

- イベントと操作の対応
- UI ロケーター
- 状態観測方法
- 具体値オラクル
- 初期化・リセット処理
- ネットワーク制御設定
- アダプター自己テスト設定

Binding はアプリケーション固有であるが、そのスキーマはフレームワーク非依存とする。

## FR-14：観測イベントの来歴

観測された変化には、次の来歴を付与できる。

- `runner`：Runner が実行したイベント
- `app`：識別可能なアプリケーション側イベント
- `unexplained`：モデル化されたイベントと対応付けられない変化

原因不明の変化は、直ちに実装バグとして確定しない。

観測不一致の証拠として保存し、必要に応じて追加検証する。

## FR-15：アダプター自己テスト

アダプターは本検証の前に、指定されたロケーターと観測操作の健全性を検査できる。

自己テストの失敗は、アダプターに依存する検査結果の信頼性に反映する。

ただし、独立して実施されたモデル検査結果を破棄してはならない。

# 7. 適合性検査・オラクル要件

## FR-16：適合性検査

Runner はモデルから生成されたイベント列を実装に適用する。

各イベント実行後に、以下を比較する。

1. モデルが予測する抽象状態
2. 実装から観測された抽象状態

不一致が検出された場合は `MODEL_DIVERGENCE` を記録する。

この不一致だけを根拠として、実装バグを `CONFIRMED` にしてはならない。

## FR-17：独立オラクル

抽象観測とは独立した具体値検証手段を提供する。

例えば、ランダムに生成した一意の文字列をフォームに入力し、リロード後に同一の文字列が保持されていることを検査する。

オラクルは、モデルの抽象状態の予測をそのまま正解値として流用してはならない。

共通の DOM 読み取り処理などが存在する場合は、その共通故障の可能性を考慮しなければならない。

## FR-18：再実行

具体値オラクルによる違反を検出した場合、同一条件で再実行できる。

再実行回数と結果を記録する。

再現性が不足する場合は `FLAKY` として表現可能とする。

再実行の結果が変化した場合も、元の観測証拠を消去しない。

# 8. 判定・レポート要件

## FR-19：判定結果

初期版は以下の5種類を使用する。

| Verdict | 意味 | Exit Code |
|---|---|---|
| PASS | 要求された検査範囲で性質が成立 | 0 |
| CONFIRMED | 有効な証拠によって性質の違反を確認 | 1 |
| INCONCLUSIVE | 検証が不十分で確定不能 | 2 |
| FLAKY | ランタイム検査の再現性が不十分 | 2 |
| ERROR | 検証機構の実行障害 | 3 |

`CONFIRMED` は、検証対象と性質を特定した違反確定を意味する。

必ずしもアプリケーション実装のバグを意味しない。

例えばモデルそのものの性質の違反も `CONFIRMED` に該当する。

## FR-20：評価対象

各判定には次の target を付与する。

- `model`
- `conformance`
- `implementation`

モデルに対する確定違反と、実装に対する確定違反を区別しなければならない。

## FR-21：証拠種別

少なくとも次の証拠種別を区別する。

- `MODEL_COUNTEREXAMPLE`
- `INDEPENDENT_ORACLE`
- `OBSERVATION_MISMATCH`

`CONFIRMED` を支える証拠は、適切な target に対する `MODEL_COUNTEREXAMPLE` または `INDEPENDENT_ORACLE` とする。

`conformance` における観測不一致のみでは `CONFIRMED` とせず、`INCONCLUSIVE` として扱う。

## FR-22：原因コード

Verdict と Cause を分離する。

初期版では以下の原因を扱う。

- `MODEL_DIVERGENCE`
- `COVERAGE_SHORT`
- `EXPLORATION_LIMIT`
- `VACUOUS`
- `UNEXPLAINED_CHANGE`
- `ADAPTER_ERROR`

Cause は verdict を置き換えるものではない。

## FR-23：集約規則

複数 target の検査結果を集約する。

有効な `CONFIRMED` が一つ以上存在する場合、overall は `CONFIRMED` とする。

それ以外の場合の優先順位は以下とする。

```text
ERROR > FLAKY > INCONCLUSIVE > PASS
```

例えば、モデルの確定違反とアダプター障害が同時に存在した場合、overall は `CONFIRMED` / exit 1 とする。

ただし、アダプター障害と未評価対象を必ずレポートに残す。

## FR-24：検証スコープ

実行時に検証対象を明示できる。

```json
{
  "targets": ["model"]
}
```

スコープ指定実行では、指定外の対象は `NOT_REQUESTED` として記録する。

スコープを指定しない通常実行では、宣言されたすべての検査対象を評価対象とする。

要求された検査の未完了を無条件に PASS として扱ってはならない。

## FR-25：レポート形式

`report.json` には少なくとも以下を含む。

- Schema Version
- 実行設定・スコープ
- Overall Verdict
- Exit Code
- Target 別結果
- Property 別結果
- Confirmed Violations
- Errors
- Not Evaluated
- Coverage
- Counterexamples
- Evidence
- Replay Results
- 実行環境と再現情報

## FR-26：反例

違反や観測不一致が発生した場合、可能な範囲で次を出力する。

- 初期状態
- イベント列
- モデルの予測状態
- 実際の観測状態
- 期待具体値
- 実測具体値
- 再実行回数と再現結果
- 反例の最小化有無

反例が最小化されていない場合は、それを明示する。

# 9. Golden Tests 要件

## FR-27：Golden Test Suite

システム自体の正しさを検証するため、Golden Test Suite を提供する。

既存の `draft-retention.golden-cases` を初期受け入れテストの基礎とする。

各ケースでは次を検証する。

- 期待 Verdict
- 期待 Exit Code
- 期待 Cause
- Target
- Evidence Kind
- 必須証拠フィールド
- 判定の不変条件

証拠全体の完全なスナップショット一致は原則として要求しない。

## FR-28：独立した模擬実装

モデルの状態遷移関数を流用しない、独立した模擬アプリケーションを用意する。

少なくとも以下の実装を持つ。

1. 正常な下書き保持
2. リロードによる下書き消失
3. ロケーター障害
4. 再現性の不安定な実行

模擬アプリケーションは実際の具体値を保持する。

## FR-29：判定不変条件

Golden Tests 全体に対し、以下の不変条件を検証する。

- 確定違反には対応する有効な証拠が存在する。
- モデル検査の決定性を維持し、モデルに FLAKY を付与しない。
- 適合性の観測不一致だけで実装バグを確定しない。
- 未評価対象と実行スコープを隠さない。
- 証拠に必要な依存先が故障している場合、無効な確定判定を行わない。

既存 Golden Suite の I1〜I5 との対応を実装時に固定する。

# 10. 非機能要件

## NFR-01：拡張性

コアエンジンを修正せず、アダプターやテスト用フィクスチャを追加可能とする。

## NFR-02：決定性

同一 IR と同一探索設定によるモデル検査は決定的であること。

探索順序と反例選択について、安定した結果を得られること。

## NFR-03：隔離性

ランタイム検証では、テストケース間の状態汚染を防ぐ。

初期版では原則として独立ブラウザーコンテキストを使用し、ストレージ・Cookie・ネットワーク等の影響を制御する。

## NFR-04：可観測性

実行失敗時に、その原因を調査可能な情報を保持する。

少なくともイベント履歴、観測結果、アダプターエラー、オラクル結果を記録する。

## NFR-05：互換性

IR にはスキーマバージョンを持たせる。

互換性のない変更は明示的に管理し、未対応形式を黙って解釈しない。

## NFR-06：安全性

対象アプリケーションに対する操作範囲を制限できること。

初期版ではローカルまたは明示的に許可されたテスト環境を想定する。

破壊的な実環境操作をデフォルトの検証フローに含めない。

## NFR-07：CI 対応

CLI で実行できること。

Exit Code によって CI が結果を判別できること。

詳細な判定・障害・未評価情報は JSON レポートから取得可能とする。

# 11. 初期受け入れ基準

## AC-01：モデル検査

`draft-retention` の抽象状態モデルを入力し、状態探索とプロパティ検査が実行できる。

同じ入力では同じ結果が返る。

## AC-02：正常実装

下書きを保持する正常な模擬アプリケーションで、要求された検査がすべて完了し、十分なカバレッジを満たした場合、PASS が返る。

## AC-03：データ消失

一意な文字列を入力し、リロードによって消失する模擬アプリケーションに対して、独立オラクルが期待値と実測値の不一致を検出し、実装 target の CONFIRMED を返す。

## AC-04：仕様と実装の不一致

抽象モデルの予測と実装から観測した状態が異なる場合、MODEL_DIVERGENCE を報告する。

観測不一致のみでアプリケーションのバグと断定しない。

## AC-05：観測障害

ロケーターが壊れている場合、アダプター依存の検査は ERROR / ADAPTER_ERROR を返す。

独立したモデル検査結果は保持される。

## AC-06：探索不足

検証に必要な探索が上限によって完了しない場合、未確定の性質を PASS としない。

## AC-07：再現性

ブラウザー実行が再実行ごとに異なる結果を返す場合、FLAKY を識別できる。

## AC-08：フレームワーク非依存性

React、Solid、Svelte で同一の UX 仕様を表現したサンプルアプリを作成する。

それぞれに対し、同一の `spec.json` と共通の Playwright アダプターを使用して検証できる。

アプリ固有のロケーター等は `binding.json` 側で変更可能とする。

## AC-09：Golden Suite

既存の Golden Cases に対し、期待結果・不変条件のすべてが通過する。

## AC-10：レポート完全性

CONFIRMED と ERROR が同時に発生した場合でも、確定違反、エラー、未評価対象、検証スコープがレポートから失われない。

# 14. 完了条件（Definition of Done）

初期版は、以下の状態を達成した時点で完成とする。

1. 宣言的な状態遷移仕様を JSON IR として読み込める。
2. モデル検査が正常に動作し、プロパティ違反と反例を検出できる。
3. Playwright を通じて実際の UI を操作・観測できる。
4. モデルと実装の不一致を検出できる。
5. 独立オラクルが具体値の損失を確認できる。
6. PASS・CONFIRMED・INCONCLUSIVE・FLAKY・ERROR を正しく判別できる。
7. Golden Tests がすべて通過する。
8. React・Solid・Svelte のサンプルアプリを、同一仕様と共通アダプターで検証できる。
9. 反例と検証結果を機械可読 JSON として出力できる。
10. 一部の検証が失敗・未実施となっても、独立して有効な検証結果が失われない。

**初期版の成功基準は、あらゆる UX を網羅的に検証できることではない。宣言的な仕様から実装を検査し、誤った実装を独立した証拠によって検出できることを、複数の UI フレームワークで実証することである。**
